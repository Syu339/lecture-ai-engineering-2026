全文投入：ツール呼び出しなし。資料全体を入力し、モデル応答1回で回答。

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
全文投入では、入力に講義資料全体が含まれており、関連するp.51～52も特定できたが、具体的な説明を回答に反映できなかった。必要な情報が存在していても、適切な回答が生成されるとは限らないことが分かった。
一方、ベクトル検索・Tree・Graphでは、質問に必要な情報を取得し、正確な回答に利用できていた。今回の質問では、検索による明確な情報不足は確認されなかった。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
今回の講義資料に対する質問応答では、ベクトル検索を基本方式として採用したい。理由は、必要な根拠を正確に取得でき、入力トークン数と生成API費用が4方式で最も少なかったためである。Graphも正確な回答を生成し、今回の測定では最も高速であったため、回答速度を重視する場合には有力な選択肢となる。ただし、今回は単一の質問を各方式1回ずつ実行した結果であり、検索・埋め込みやキャッシュの影響も考えられる。また、生成API費用に索引構築分は含まれていない。複数ページの統合が必要な質問や資料にない情報を尋ねる質問などで追加検証が必要である。
- 気づき・疑問：
全文投入はモデル応答が1回でも、入力トークン数が多く、費用が高かった。
ベクトル検索は最も低コストだった一方、今回の回答時間は最も長かった。検索処理やキャッシュなどの影響を調べたい。
Treeは目次をたどることで根拠を特定できたが、モデル応答回数が多くなった。
Graphは高速かつ正確だったが、質問や資料の構造が変わっても同様の優位性があるのか検証したい。
今後は複数ページの情報統合、根拠不足時の回答抑制、回答品質の定量評価を比較したい。

## 宿題

- **取り組んだレベル：** 基礎

- **やったこと（変更したファイル・設定・処理、または設計した取得方法）：**
  `app/agent.py`の`INSTRUCTIONS`を1か所変更し、複数の話題を含む質問の検索戦略を比較した。
  変更前は「必要に応じて検索を分けて根拠を集める」という指示だったが、変更後は「複数の話題を含む質問でも検索語を工夫して`search_materials`を1回だけ呼び出し、根拠が不足する場合は推測せず確認できないと伝える」とした。
  検索回数を削減することで、回答品質を維持しながらトークン数と生成API費用を削減できるか検証した。

- **比較した質問と、固定した条件（モデル・対象資料など）：**
  質問：「第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか？」
  モデルは`gemini-3.5-flash-lite`、対象資料はAIエンジニアリング実践講座2026の第1～3回、検索方式は通常のベクトル検索に固定した。同じ質問を`--trace`付きで実行し、指示文以外の設定は変更しなかった。

- **結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：**
  | 評価項目 | 変更前 | 変更後 |
  |---|---|---|
  | 検索回数 | 2回 | 1回 |
  | 回答時間 | 4.13秒 | 11.87秒 |
  | 入力トークン | 6,547 | 2,552 |
  | 出力トークン | 437 | 361 |
  | モデル応答回数 | 3回 | 2回 |

  | 回答品質 | おおむね正確 | おおむね正確 |
  | 引用ページ | 第3回 p.13、39、40、65 | 第3回 p.13、39、40、65 |

  **変更前のツール呼び出し：**
  - `search_materials({'query': 'コンパクション セッション メモリ'})`
  - `search_materials({'query': '日々のメモ 長期メモリ すべて'})`

  - `search_materials({'query': 'コンパクション セッション メモリ 長期メモリ 日々のメモ 第3回'})`

- **改善した例と、残る失敗・制約：**
  今回の質問では、2つの論点を1つの検索クエリに統合することで、回答内容をおおむね維持しながら生成API費用を削減できた。
  一方、回答時間は増加した。API応答時間などの影響も考えられ、各条件1回の測定では原因を特定できない。また、`--trace`では検索結果の本文が省略されるため、引用されたすべてのページが実際に取得されたかまでは確認できていない。複雑な質問では、検索を1回に制限すると必要な根拠を取りこぼす可能性がある。

- **気づき・疑問：**
  検索回数を増やすことが必ずしも回答品質の向上につながるわけではなく、検索クエリの設計が重要だと分かった。今回の実験では、検索回数の削減がトークン数と費用の削減につながったが、処理時間は短縮されなかった。
  実務でRAGを運用する場合は、検索を常に1回に制限するのではなく、まず統合検索を実行し、根拠が不足する場合に追加検索する適応型の戦略が有効ではないかと考えた。
  今後は質問の複雑さに応じて検索回数を調整する仕組みや、回答品質と費用の最適なバランスについて検証したい。
